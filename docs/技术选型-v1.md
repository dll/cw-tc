## 1. 结论（先行）

| 层 | 选型 | 状态 |
|---|---|---|
| **学生端（主战场）** | **Flutter 3.22+（Dart 3.4+）**，单代码库输出 **Android / Web**；**iOS / 鸿蒙不做**（Flutter 保留扩展位，后续可低成本补） | 已定 |
| **管理端**（阅卷台 / 内容管理 / 订单 / 证书台账 / 广播） | **Vue 3 + Vite + Element Plus + Pinia**（桌面优先 Web，**含教师工作台**） | 已定 |
| **对外静态页** | **Go 模板直出**（验真 `/verify`、隐私政策、用户协议、退款政策） | 已定 |
| **后端** | **Go 1.26 + Gin**（单二进制）；REST + JSON，OpenAPI 契约 | 沿用 PRD §11.2 |
| **数据** | **PostgreSQL 15+**（事务 / JSONB / **pgvector**） + **Redis**（会话 / 验证码 / 限频 / **AI 额度计数**） | 沿用 + v1.1 增补 |
| **支付**（v1.1 新增） | **微信支付（Native / App）+ 支付宝（当面付 / App）** | **待确认组合**（PRD v2 §16-12） |
| **AI**（v1.1 新增） | **自建 AI 网关** + **国内合规大模型服务** | **待确认供应商**（PRD v2 §16-14） |
| **静态资源** | **腾讯云 COS + CDN**（课件 / 音频 / 视频 / 冻结输出） | 沿用 PRD §11.2 |
| **制证** | **Chrome headless**（HTML → PDF），复用上游 `_make_certs.py` 路线 | 沿用 PRD §11.2 |

**一句话边界**：**Flutter 管"学生怎么用"，Vue 管"老师怎么管"。** 后台是表单密集、桌面优先的场景，
硬塞进 Flutter 只会把两件事都做坏 —— 所以这里**故意不追求"一套代码全包"**。

**为什么支付与 AI 要做"网关层"而不是业务直连**（v1.1 要点）：

- **可替换**：商户号 / 模型供应商变更只改网关配置，业务代码零改动；
- **可审计**：所有资金动作与模型调用统一留痕（`payment_txn` / `ai_message`）；
- **可兜底**：回调验签、幂等、额度、内容审核这些**必须集中做一次**，散在业务里必然漏；
- **凭据集中**（v1.1 补）：**支付 / 模型 / 短信的密钥只被网关读写**，业务层拿不到原文；
  密钥经 `shared/.env` 注入（模板 `deploy/.env.example`），**照同系列项目一样处理**
  （对照 ccit 的 `/etc/ccit/ccit.env`）。

**向量库为什么选 pgvector 而不是独立向量数据库**：本产品语料是**自有课程资产**（7 门课），
量级不大；用 pgvector 可**复用既有 PostgreSQL**，少一个运维组件、少一套备份策略。
若将来语料量级跃升，再由 `kb_chunk` 这层抽象平滑迁移。

## 2. 决策依据：既有技术栈（**本机实测，非推测**）

选型不是从零比较，而是**在既有工程资产上做减法**。以下为同级仓库实测结果
（2026-10-03 直接读文件得到，非记忆）：

| 项目 | 后端 | 前端 | 实测证据 |
|---|---|---|---|
| **ccit**（畅网官网） | Go（`packages/server`） | **Flutter Web** | `packages/web/pubspec.yaml` → `name: ccit_web`、`description: "…（Flutter Web）"`、`sdk >=3.4.0`，含 `web/` 目标 |
| **wxx**（蔚小芯） | Go（`go.mod`） | **Flutter 多端**：`android / ios / linux / macos / harmonyos / web` + **独立原生微信小程序** | `frontend/pubspec.yaml` → `name: wxx_app`、`sdk ^3.4.0`；平台目录逐一存在；`frontend/miniprogram/` 为原生小程序（`app.json`/`app.wxss`） |
| **tsloms** | Go + Java 双后端 | 管理端 **Vue 3 + Vite + Element Plus + Pinia** | `packages/admin/package.json` → `tsloms-admin`，deps 含 `vue@^3.4` / `element-plus` / `pinia` / `echarts`，devDeps 含 `vite@^6` / `vitest` |
| **cw-vopc / eqs** | — | pnpm + TS monorepo（部署流水线侧） | `pnpm-workspace.yaml`、`vitest.config.ts` |

**三条可复用的既成事实**：

1. **前端 = Flutter 是本系列的事实标准**（ccit、wxx 两处独立验证）。
2. **"多端一致"在本系列已有先例**：wxx 正是用一套 Flutter 出六端，
   **并且已经踩过"小程序要单独写"这条线**（`miniprogram/` 是原生目录，不是 Flutter 编译产物）。
3. **管理端 = Vue 3 + Element Plus** 也是既有标准（tsloms），无需另创一套。

> AGENTS.md 写明"沿用 CCIT / TSLOMS 同一套工程规范"。上面这套栈**就是**那条规范，
> 选择它不是偏好问题，是**一致性成本最低**。

## 3. 学生端为什么是 Flutter（而不是别的）

### 3.1 备选对比

| 方案 | 多端一致性 | 移动端体验 | Web 端质量 | 本系列经验 | 结论 |
|---|---|---|---|---|---|
| **Flutter** | **最强**（Skia/Impeller 自绘，跨端像素级一致） | **接近原生**（编译为 ARM 机器码，非套壳 H5） | 可用；**首屏偏重**、SEO 弱 | **ccit + wxx 两处现成** | **选它** |
| React Native + Expo | 中（原生控件，各端观感有差） | 好 | RN-Web 成熟度一般 | 无 | 否 |
| uni-app（Vue 系） | 中 | 中（可出小程序，这是它唯一优势） | 尚可 | 无 | 仅当**必须小程序为主**才考虑 |
| Taro（React 系） | 中 | 中 | 尚可 | 无 | 同上 |
| 原生（Kotlin + Swift）×2 + 独立 Web | 差（三份代码） | 最好 | 需另写 | 无 | 人力不允许 |
| PWA | 中 | **不是 App**（无法上架、推送受限、无法离线装包） | 好 | 无 | 不满足"移动应用为主" |

### 3.2 关键结论：**"多端一致"是 Flutter 的本职工作**

- 刘老师的要求是"**多端一致**，移动为主"。Flutter 用**自绘引擎**把 UI 画到每个平台，
  同一份 Dart 代码在 Android / iOS / Web 上**渲染结果与交互逻辑同源** —— 这是"一致"最接近字面解的方案。
  RN/uni-app 走的是"映射到各端原生控件"，一致性天然打折。
- "移动应用为主"意味着**不是套壳 H5**：Flutter 编译出的是原生二进制，
  能上架应用商店、能收推送、能本地缓存课件音频（学生**弱网/地铁**场景是刚需，见 PRD §8 特色八）。

### 3.3 Web 为辅 —— SEO 弱这个劣势，在本产品**不成立**

Flutter Web 常被打的短板是"内容页搜不到"。但本产品的获客路径是**学校/课堂导入 + 课程码**，
不是搜索引擎自然流量：

- 课程广场、课程详情是**登录后**才能用的功能页，本就不承担 SEO 职能；
- 对外需要被搜到的只有**验真页**（PRD §7.4 D-4：`/verify`）——
  这一页**单独用服务端渲染的轻量 HTML**即可（Go 模板），**不需要走 Flutter Web**。

> **所以**：**验真页 + 隐私政策等对外页用 Go 模板直出；学生端功能页全部走 Flutter Web。**
> 这条分工把 Flutter Web 唯一的实质短板绕开了。

## 4. 管理端为什么单独用 Vue 3

| 维度 | 阅卷台 / 内容管理 / 台账 的真实形态 | 谁更合适 |
|---|---|---|
| 交互形态 | **表单密集**：采点打分、批量操作、表格筛选、导出 CSV | **Vue 3 + Element Plus**（现成表格/表单组件） |
| 屏幕 | **桌面优先**（≥1280 px），助教用电脑批卷 | 桌面 Web |
| 复用 | tsloms 管理端**已经跑通**这套（含 vitest + eslint + e2e smoke） | 直接沿用规范 |
| 若用 Flutter | 需自建表格/表单/级联筛选，**投入产出比差** | 不选 |

## 5. 多端一致的真实边界（**哪些必须分叉，先说清楚**）

"一套代码"不等于"零分叉"。以下差异是**设计内的**，不是缺陷：

| 项 | App 端 | Web 端 | 处理 |
|---|---|---|---|
| **HTML 课件（含动画/节拍）** | **必须 WebView** | iframe | 原生渲染还原不了课件动画，**硬约束**（见 PRD B-3） |
| 音频/视频 | 原生播放器（just_audio / video_player），支持后台播放、倍速、记忆位置 | 浏览器播放器，后台播放受限 | 按端能力降级 |
| 离线 | 可缓存课件/音频（弱网刚需） | 浏览器缓存 | App 端为增强项 |
| 布局 | 手机单栏，底部导航 | 宽屏多栏 | 按断点分叉（非两套代码） |
| 推送 | 系统推送 | 站内消息 | App 端为增强项 |
| 颜文字/等宽冻结输出 | 需内嵌等宽字体 | 同 | 字体随包/随 CDN |

**验收口径**：同一功能在两端**正文与数字必须一致**；**表现（布局/播放器）允许有差异**。

## 6. 关键风险与对策（**含"本机未实测"的如实标注**）

| # | 风险 | 影响 | 对策 / 现状 |
|---|---|---|---|
| 1 | **Flutter Web 首屏体积大**（CanvasKit + 中文字体） | Web 端首屏可能明显慢于 App | **未实测** —— 本机没有构建产物，**不给数字**。上线前实测后再定 Web 首屏指标；减重手段：字体子集化、deferred loading、优先 HTML/WASM 渲染器 |
| 2 | HTML 课件在 App 端只能 WebView 渲染 | 动画/节拍表现与浏览器可能有差 | 写进 B-4 验收：**正文与数字一致**即可；上线前对**体量最大的课件**（>10 MB）做真机抽测 |
| 3 | ~~iOS 上架需 Apple 开发者账号~~ | — | **已消除**：iOS 不做（2026-10-03 拍板） |
| 4 | ~~鸿蒙支持依赖 Flutter 鸿蒙分支~~ | — | **已消除**：鸿蒙不做 |
| 5 | 多媒体资源体量大（单课 374 条音频） | 流量与 CDN 成本 | 走 COS + CDN，音频转码压缩；App 端可预下载指定讲 |
| 6 | 两端行为不一致导致的缺陷 | 返工 | 验收清单**按端分列**（见 §5），CI 里 App/Web 各自构建产物都要过 smoke |
| **7** | **AI 首字延迟不可控**（模型 + 网络） | 体验 | **未实测** —— 无模型配额，**不给数字**（PRD v2 §11.4）；对策：流式输出 + prompt 精简 + 区域就近接入 |
| **8** | **支付回调漏单 / 重复** | **资金差错（严重）** | 网关层统一做**验签 + 幂等键 + 对账**（PRD v2 §7.3 G-2/G-3） |
| **9** | **模型供应商变更 / 数据出境** | 合规 + 返工 | AI 网关抽象；**优先国内合规模型**；不向模型发送个人信息 |

> **规矩照旧**：上面凡是没实测的数字，一律不写数。**"未实测"比一个漂亮的假设值有价值。**

## 7. 不做什么（明确排除）

- **不用 Flutter 做管理后台** —— 表单/表格场景投入产出比差（§4）。
- **不用 PWA 冒充 App** —— 上不了商店、推送受限，不满足"移动应用为主"。
- **首发不做 iOS / 鸿蒙 / 微信小程序**（2026-10-03 拍板，见 §8）。
  Flutter 主栈**保留 iOS 与鸿蒙的扩展位**（补端成本低）；小程序若将来要做，
  **沿用 wxx 的做法：单独写原生小程序**（Flutter 官方不支持编译到小程序，如实说明、不硬凑）。
- **不为多端维护多套业务逻辑** —— 业务逻辑一律在 Go 后端；前端只做展示与交互。
- **不让业务代码直连支付渠道与大模型** —— **必须走网关层**（§1），否则验签、幂等、额度、审核必然做漏。
- **不引入独立向量数据库** —— 用 pgvector 复用既有 PostgreSQL（§1）。
